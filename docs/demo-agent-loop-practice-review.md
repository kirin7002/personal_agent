# 方案一：开源实现对照与优化建议

日期：2026-11-15  
范围：单实例 Demo 的 Agent Loop 功能、交互和效率。本文记录调研建议。后续已完成 [原生 steer 隔离验证](hermes-native-steer-verification.md)，尚未正式接入页面；原生 clarify 仍未做功能验证。方案二尚未决策。

## 1. 结论

本文件保留调研依据，整合后的实施范围与优先级以 [方案一主文档](demo-agent-loop-optimization-plan.md) 为准。

方案一的大方向可保留，但应更明确地收敛：**复用一个 Hermes 循环，补少量业务状态和控制接口，而不是再搭一套通用 Agent 引擎。**

优先解决三个问题：

1. 用户的新消息属于回答、改口、排队追加、闲聊还是新任务？
2. 当前任务是完成了，还是在等用户、等时间、等外部结果？
3. 哪些新信息值得再调用模型，哪些处理可以由程序直接完成？

以下比较针对公开机制，不代表这些项目在我们的车辆用例上已经做过性能对照。没有证据证明换框架本身会使 Demo 更快。

## 2. 核对到的公开实现

| 实现 | 明确提供的机制 | 可借鉴的点 | 不直接照搬的部分 |
| --- | --- | --- | --- |
| Hermes | 模型/工具循环、消息历史、可中断调用、预算及扩展接口 | 当前 loop 应继续复用；先核对原生控制能力再补适配层 | 不为“统一架构”重写相同循环。[官方循环说明](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop) |
| Hermes Runs API | 运行中指导接口，以及绑定原生控制请求的 clarify 响应接口 | 候选方案可减少应用层停止/新建 run 的控制流程 | 应用自建追问不是原生控制请求，不能直接把 task_id 填进 clarify 接口；是否节省后续推理还需测。[API 文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server) |
| LangGraph | 显式 interrupt、同一 thread 的 resume、结构化暂停数据 | 等待状态和继续事件必须有明确身份与返回值 | 恢复会重新执行被中断节点的前部代码，不是任意语句级继续；这里借鉴语义，不迁移框架。[官方 Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) |
| Pydantic AI | Deferred Tool Requests/Results，按工具调用标识匹配迟到结果；区分需要模型修正与普通失败结果 | 外部工具未完成时，明确记录“等哪一个结果”，收到后续回同一次业务工作 | 其类型/异常属于该框架，不能直接放进 Hermes 的 MCP 工具就期待生效。[官方 Deferred Tools](https://ai.pydantic.dev/deferred-tools/) |
| Pi Agent Core | steer 与 follow-up 分开排队；上下文转换与 UI 事件分开；有每轮结束控制点 | 区分运行中改变方向与当前工作结束后的追加输入，减少消息误归属 | follow-up 队列不是定时器；不得把框架的输入排队误当成“十秒后执行”。[官方源码说明](https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/agent/README.md) |

## 3. 本机 Hermes 的核对结果

本次只读检查确认：

- 对外能力声明包含 `run_steer=true`，对应运行中指导入口。
- 安装版本的源码与文档包含 `/v1/runs/{run_id}/clarify`；必须对应已经存在的原生控制请求。本次能力输出没有单独的 clarify 功能字段，也没有实际触发原生追问验证。
- 当前 API 工具集只启用车辆 MCP。现有 `request_user_input` 在应用任务表写入等待状态，随后应用停止远端 run；用户回答后建立新的 run、继续原 Hermes 会话。
- 当前车辆 MCP 请求超时配置为 10 秒。因此不能把“十秒后查温度”简单实现为工具函数睡十秒；等待会占着请求，并可能遇到超时。

这些结果只证明接口/源码存在和当前配置边界，不证明原生追问能直接替换现有实现。还需验证等待是否占运行额度、计时预算怎样处理、取消行为和上下文接续。

## 4. 优化一：保持单一循环，把新增职责缩成小接口

建议新增内容优先表现为函数与状态记录，而非独立服务或第二个调度框架：

| 业务接口 | 负责什么 |
| --- | --- |
| EventRouter | 明确输入归属及事件类型，不执行工具、不反复规划 |
| TaskView | 原目标、有效约束、已知工具引用、事实回执、当前等待与待办的简短视图 |
| WaitRegistry | 记录等待原因、关联对象、触发条件和接续方式 |
| ResultPolicy | 已有校验、类别推导、无进展判断与反馈决策 |

Hermes 继续负责对话 transcript 与模型/工具循环。TaskView 不复制全部聊天历史，也不成为另一份独立更新的“模型记忆”。已有字段和回执优先投影复用，仅在开始、补充、改口或等待结束等时机提供必要更新。

Hermes 的 Context Engine 是接管上下文压缩/选择的扩展，不是普通业务状态容器。现阶段没有必要为几个任务字段替换它；只有测到明确的长上下文问题才考虑相关扩展。[Context Engine 文档](https://hermes-agent.nousresearch.com/docs/developer-guide/context-engine-plugin)

## 5. 优化二：把消息处理分成不同动作

| 输入 | 应用语义 | 例子 |
| --- | --- | --- |
| 回答追问 | 回答已知问题，继续原目标 | “全部”回答空调分区 |
| 运行中改口 | 修改当前目标或约束，旧目标结果不能覆盖新目标 | “改成21度” |
| 排队追加 | 当前任务结束后再处理附加要求 | “做完再告诉我详细参数” |
| 闲聊/礼貌回应 | 前台对话，不自动修改任务 | “谢谢” |
| 新需求 | 建立独立任务 | “再打开天窗” |
| 取消 | 停止指定任务；不等同于普通插话 | “取消刚才那个设置” |

借鉴 Pi 的不同输入通道，但具体任务关系由我们的前台/协调器确定。沿用 S2S 的现有意图判断，以及文字界面的明确任务选择，不增加每条消息必经的额外路由大模型。

## 6. 用户提出的重点：运行中改口如何实现

以“全部空调设为23度”，执行中改为“21度”为例，建议的应用流程是：

1. 前台把新输入归为 `revise_goal`，明确指向原 task；存在歧义先确认，不能盲改最近一个任务。
2. 保存原始要求与新的有效目标，更新处理轮次。页面显示“已收到修改，正在按21度处理”，不提前宣布完成。
3. 对尚未提交的旧23度工具调用/完成结论，按旧轮次拒绝或标记过期。已经生成的旧预览保留为历史、标记被替代，不计入新目标完成。
4. 在原运行仍接受指导时，候选实现是调用 Hermes steer，传入新目标与有效上下文。模型在其支持的处理边界消费更新，而不是假定立即撤销已经开始的工具。
5. 收到“accepted”仅表示已接受指导；还需确认后续执行采用了新轮次和21度目标。
6. 若原生指导不可用，应用可结束当前 run，再在原业务 task、原 Hermes 会话上建立一个带新目标的 run。不能因此新建一个丢失前文的“改成21度”任务。

边界处理：

| 当前阶段 | 应有行为 |
| --- | --- |
| 模型尚在生成旧参数 | 接收修改，阻止旧轮次输出被当成当前结果 |
| 23度预览已经生成，但任务未终结 | 保留旧记录并标记被替代，继续生成21度 |
| 原任务已经完成 | 建立关联的新请求，复用明确的对象/分区信息，不改写旧任务历史 |
| 同时有多个可能目标 | 先确定修改哪一个，不靠“改成”二字猜测 |

必须验证的现有代码耦合：`TaskManager.run` 看到本地 revision 改变会停止原 run；MCP 入口也会拒绝旧 revision。原生 steer 的接入必须同时协调这些检查和“新目标已生效”的边界，不能只新增一个 HTTP 调用。

控制回执的可用性也要随目标版本变化：旧23度回执不能完成新21度目标；仍有效的工具定义和查询事实可复用，不必重新翻目录。当前没有真实车辆执行，因此“替代旧预览”不代表撤回真实设备动作。

本节保留验证前的设计分析。原生 steer 后续已完成隔离实测，六次受保护用例通过；当前仍未正式接入前台，具体必要适配及限制见 [验证报告](hermes-native-steer-verification.md) 和方案一主文档。

## 7. 优化三：统一等待记录，保留三种不同语义

建议 WaitRecord 至少包含：关联 task、处理轮次、wait_id、等待类型、预期输入/结果、触发条件、接续后端、状态及预算。

| 等待类型 | 等什么 | 如何继续 |
| --- | --- | --- |
| user_answer | 对一个明确问题的回答 | 校验问题与轮次，把答案送回对应继续入口 |
| timer | 尚未发生的时间点；业务工具可能还未调用 | 到点执行原目标的下一步，不伪造一份工具结果 |
| external_result | 已经发起的异步工具/作业结果 | 按原调用/作业引用回填，不能把另一项结果接过来 |

LangGraph 的明确暂停状态、Pydantic AI 的调用与回填关联，都支持这种区分；但实现语义不能互相混用。对 Hermes 应通过适配器选择原生等待或现有应用层“结束本次运行、在原会话继续”的方式。

不要一开始就重构已通过测试的追问路径。先验证原生 clarify 是否带来可观测的简化或收益，再决定是否替换；回答一个原生暂停不等于以后生成参数不再需要模型推理。

## 8. 优化四：定时继续先做最小闭环

第一条用例仍是“收到请求后10秒查询空调温度”。

- 时间基准由程序确定；不要让模型把“等十秒”理解成从很久之后的工具调用时刻重新计算十秒。
- 在任务控制层记录一次时间等待，到期发继续事件，不在现有车辆 MCP 内长时间 sleep。
- 等待阶段没有模型空转，当前目标和已知工具保留。
- 第一次取消后，迟到的到期事件不执行任务。
- 当前不做周期任务、生产调度或外部真实车控完成监控。

对 pending/done 异步工具，先定义结果引用和状态协议，再用明确的测试替身验证。当前即时返回的车辆预览不能凭空变成“设备正在执行”。

## 9. 优化五：失败信息决定处理方式，而不是一律重问模型

| 情况 | 推荐处理 |
| --- | --- |
| 结果标签等可由回执确定的字段 | 沿用现有程序推导，不增加模型修正轮次 |
| 模型参数不合 Schema | 返回明确缺失/冲突字段；确有必要才让模型修正或向用户追问 |
| 明确业务限制或未配备 | 按缺失事实补查；证据足够后解释并结束，不无限重试原动作 |
| 暂时性的服务错误 | 程序按现有有限重试规则处理；不要每次让模型重新决定网络重试 |
| 合法的时间/外部等待 | 等事件，不当作错误或成功 |
| 相同动作、相同参数、相同事实下反复失败 | 识别无进展，停止重复尝试或澄清 |

无进展比较应看有意义的事实值和失败条件，不能因为回执 ID/时间戳变了就认为有新信息。正常的有限等待轮询要单独计数，不能与错误循环混为一谈。这是本项目的策略建议，不是将其他框架的重试异常原样复制进来。

## 10. 优化六：单一事件流，分别展示运行与任务结果

Hermes 的运行结束、一次工具返回、任务目标完成和语音播放结束是不同事件。沿用现有页面过程展示，补齐等待/改口/继续的事件映射即可。

应用结果仍以有效业务回执和完成提交为依据，不拿框架的 agent_end 或一段最终文本直接判成功。事件仅用于展示时，不要回灌成模型的新用户指令，也不要为每条过程消息额外调用总结模型。

## 11. 建议修订后的推进顺序

1. **先固定三个契约**：TaskEvent、TaskView、WaitRecord，明确每个字段由谁更新及如何关联。
2. **按 steer 验证结果正式接入，单独验证 clarify**：steer 已证实需要目标版本、旧参数/回执与监控适配；clarify 的继续语义、等待额度和超时行为仍未做功能验证。
3. **按验证结果接入最小适配**：优先复用 Hermes；不满足要求时保留应用层继续机制。
4. **实现一次定时继续和异步结果测试替身**，不扩展周期调度。
5. **验证轮数与正确性**：普通设温、相对升温、缺参回答、运行中改口、相同失败、等待取消。每条重复多次、交错对照，区分模型推理时间、控制开销和等待时间。

方案二仍未决策；不实施子任务并发，也不以其拆分/汇总设计作为本轮必须完成的内容。

## 12. 证据边界

最初调研仅完成官方文档/源码、项目代码及本机能力的只读核对。之后原生 steer 已在独立实验实例中完成验证，但没有正式接入业务页面；原生 clarify 仍未做功能测试。本轮合并仅更新方案文档，没有新增运行代码改动。

这些公开实践支持的是清楚的状态和接口边界，不是一个对所有场景都成立的“最快框架”结论。当前方案应依据这些边界收敛，再用 Demo 验证。
