# 根据回执自动判定成功结果类型

状态：已实现，沿用现有 Hermes、工具协议、校验与通知链路。

## 解决的问题

此前，模型同时引用查询与控制回执，却提交 `outcome=prepared`，程序会返回 `INVALID_OUTCOME`，使模型再调用一次 `finish_task` 修正为 `mixed`。这个标签可由实际回执确定，不需要模型重新推理。

现在目标已完成时，`finish_task` 可以省略 `outcome`，默认 `auto`。程序在现有事务内校验回执后分类：

| 有效引用 | 最终类型 | 前台状态 |
| --- | --- | --- |
| 只有车控预览 | `prepared` | 模拟成功 |
| 只有模拟查询 | `answered` | 查询完成 |
| 两者都有 | `mixed` | 模拟成功，保留查询证据 |

旧客户端提交 `prepared` 或 `answered` 且实际同时引用两类成功回执时，会直接规范化为 `mixed`，不返回类型错误。旧类型仍然主张某种结果、却完全没有对应成功回执时继续拒绝；例如声称车控完成却只有查询回执，不通过静默改成查询完成来掩盖缺失操作。

**程序判定的是结果类别，不是自然语言任务是否已经全部完成。** 多步任务仍由 Agent 调用一次 `finish_task` 宣告完成并提交摘要/证据。此次省掉的是类型修正重试；没有扩展为“任何查询或控制成功就提前结束”。

## 保留的约束

- 未知、跨任务回执或过期/取消任务，继续拒绝。
- 引用中含错误或 `unresolved` 非空，不自动报告全部成功。
- `auto` 遇到历史调用失败，且没有本次引用的同工具后续成功回执解决它，要求明确的业务结论，不把失败隐藏在查询成功后面。
- `unsupported`、`partial`、`failed` 仍由 Agent 明确提交，并保留原证据、诊断与未完成项校验。
- 已修正的参数重试可使用后续有效回执；失败处理不会因错误标签被自动变成成功。
- 分类、结果保存和唯一完成通知在同一事务提交，重复完成不重复通知。
- 最终结果 JSON 仍使用原有六种规范类型，不存储 `auto`；导入导出及业务工具配置没有变化。

## 结束后的多余请求

本地 Hermes 中间件原先只在单项控制直接完成后抑制下一次模型请求。现在，对于程序已校验并提交的成功终态，也由本地、零 token 的终止响应结束运行，不再启动无业务必要的尾部模型回复。

只有数据库中的有效成功终态与分类事件触发这条路径。失败/未完成的任务继续原循环；不是根据模型文本中的“成功”二字提前结束。

页面将显示“程序判定结论类型”和“程序校验回执并提交结论”，并保留原提交类型及最终类型的本步数据。

## 简单指令的候选包

针对简单场景负担增大的反馈，新增保守的精简策略：单个高置信度控制候选，且请求匹配明确示例或含明确绝对目标表达、没有相对/条件/查询标记时，只预加载控制定义。相关车况/车书定义及路径留给后续按需搜索。

这只是检索策略，不生成参数、不授权执行，也不扩大直接完成资格。缺参数仍需追问；相对调节、复杂请求和不确定情况仍可加载关联查询，运行中始终保留全局搜索。

## 实测

相同指令按修改前、修改后顺序各执行一次；没有随机交错，样本较少，后台耗时不含 S2S。

| 指令 | 修改前 | 修改后 | 类型修正轮次 | 提供方请求尝试 |
| --- | ---: | ---: | ---: | ---: |
| 空调温度增加一度 | 9.19 秒 | 9.19 秒 | 1 → 0 | 5 → 3 |
| 主驾空调温度增加一度 | 12.82 秒 | 6.35 秒 | 1 → 0 | 5 → 3 |
| 空调温度增加一度，重复 | 10.25 秒 | 6.72 秒 | 1 → 0 | 5 → 3 |
| 查询当前空调温度 | 4.58 秒 | 3.18 秒 | 0 → 0 | 3 → 2 |

相对温度三条样本的中位后台耗时为 10.25 → 6.72 秒。请求尝试减少两次，分别来自省掉类型修正和抑制终态后的收尾请求；收尾请求原本可能被取消，不在任务完成耗时内，因此不能将两次减少都当作完整等待轮次。首条虽然减少了请求，耗时仍为 9.19 秒，显示远端延迟波动仍然存在。

另对“全部空调温度设置为21度”各测三次：

- 候选包：2686 → 893 字符。
- 提供方请求：两组都为 1 次，工具和参数全部正确。
- 中位后台耗时：2.21 → 2.40 秒。

这组小样本没有证明精简候选包带来稳定提速，不能把结果写成“所有简单场景都更快”。精简策略减少了不必要的候选输入，但模型、网络和排队的影响仍需更多交错样本才能分离。
