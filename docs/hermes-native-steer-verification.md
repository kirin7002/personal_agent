# Hermes 原生 steer 接入验证

日期：2026-11-15  
状态：隔离验证已完成；未接入当前页面或 S2S 改口入口，未实施方案二。

## 结论

**可以在同一个 Hermes run 中处理“23度改成21度”，但不能只调用 steer API。**

原生 steer 负责把新的指导送入后续处理边界，不能撤回已经在执行或已准备提交的工具调用。本项目还需要同步任务目标/轮次、拒绝旧参数、排除被替代的旧回执，并适配原监控器。

六次受保护的真实模型验证全部通过：任务和 run 均不更换，最终只保留21度控制结构，改口后没有接受23度控制回执，只产生一次完成通知。

这里“接受/生效”指工具服务接受控制预览并将其作为当前结果，**不是实际车辆温度变化**。没有连接车辆，也没有测试真实设备撤销。

## 1. 测试方法

为排除缺少分区的追问，初始指令为“把所有分区空调设为23度”，执行中改为“把所有分区空调设为21度”。

- 使用当前安装的 Hermes 源码、现有 DeepSeek 模型、当前业务工具定义和校验实现。
- 单独运行测试网关，独立配置、API Key、任务数据库和会话存储；共享已安装依赖。
- 使用真实 `/v1/runs/{run_id}/steer`，不是本地假响应。
- 复用现有任务输入组装、预加载、MCP 通用协议和业务回执格式；实验适配代码仅在 `experiments/steer_probe/`。
- 工具提交前和结论提交前使用测试停点，精确制造改口交错；这不是性能测试，也不是靠随机等待碰运气。
- “模型生成中”用例未暂停模型，通过请求开始/响应完成记录确认改口发生在第一轮请求期间。
- 不把模型返回的23改写成21。模型若提交旧目标，适配层拒绝；成功必须来自模型实际生成的21度参数。

## 2. 真实模型结果

每类执行两次：

| 用例 | 观察结果 | 说明 |
| --- | --- | --- |
| 只发原生 steer，不更新应用轮次/目标保护 | 两次接口都接受；两次旧23度调用仍在改口后被接受，之后模型才生成21度 | 接口 accepted 不保证旧调用不会继续通过 |
| 更新应用轮次，但使用原 TaskManager 监控逻辑 | 没有形成21度完成结果；补充审计确认原监控器发出 stop，远端变为 cancelled | 原逻辑发现 revision 改变就停止 run，不能直接接原生 steer |
| 模型生成中改口，启用实验适配 | 2/2：原 task、原 run，最终21度；旧23度回执为0 | 旧轮次工具调用被拒绝，模型继续按新目标处理 |
| 23度调用提交前改口，启用实验适配 | 2/2：原 task、原 run，最终21度；旧23度回执为0 | 直接完成模式也不能绕过旧轮次检查 |
| 23度预览已保存、最终结论提交前改口 | 2/2：旧23度记录保留，最终只引用21度；完成通知一次 | 为明确命中该窗口，本用例关闭单项直接完成，使用普通结论提交路径 |

完整正式集合为10次，另增加2次原监控器停止请求审计。六个受保护用例全部成功；两个原生裸调用对照显示缺少保护，四个原监控器对照/审计显示监控逻辑需要适配。早期启动调试不计入正式集合。

最终结果和统计见 [验证数据](../benchmarks/results/hermes-native-steer-verification.json)。原始实验轨迹保存在被忽略的 `test-results/steer-probe.json` 和 `test-results/steer-stock-monitor-audit.json`；不发布原始请求、凭据或私有网关日志。

## 3. 实验中补了哪些适配

### 3.1 先更新业务目标，再发 steer

在本地事务中更新有效目标和处理轮次，清空当前预览视图，保留旧回执作为历史。随后向原 run 发送新目标、当前任务身份和轮次。

这样即使旧23度调用先到，也会因旧轮次被拒绝。steer 接收失败时不能退回继续执行旧目标；正式接入还需要明确失败/重试交互，本次没有实现页面上的这部分。

### 3.2 两层参数保护

- 沿用当前 MCP 对 task_revision 的检查，拒绝旧轮次调用。
- 实验额外绑定本次明确温度目标，拒绝“新轮次但仍提交23度”的调用，禁止静默改写参数。

第二层仅针对测试中明确的空调温度变更。正式功能需要前台/协调器形成可校验的结构化修改约束，不能把本次测试当作任意自然语言目标都能自动判定。

### 3.3 新目标不能引用旧控制回执完成

当前主程序的最终结论读取本任务所有历史回执，不按目标版本自动排除旧控制记录。实验增加了旧轮次控制证据拒绝规则，避免旧23度回执被重新标为新目标的成功证据。

单元测试另外验证了：把旧回执和新回执一起引用也会被拒绝；旧记录仍可审计；任务完成后不允许悄悄改写为另一个目标。

### 3.4 原 run 的监控与完成绑定

原 `TaskManager.run` 在 revision 不一致时停止远端。实验协调器只允许明确登记过的改口轮次继续监控同一个 run，未知变更仍拒绝。

完成中间件也需要稳定的任务绑定：当前实现按请求中的目标字符串和轮次查找任务，改口后旧输入不再匹配。实验使用已登记的初始任务身份进行追踪和本地收尾，避免为了完成再启动无用的模型请求。正式接入应明确原始目标、有效目标及运行身份的关系，而不是简单放宽所有匹配。

## 4. 校验与边界

新增4项保护测试，覆盖：

- 旧轮次23度被拒绝；新轮次携带旧23度同样被拒绝。
- 新21度参数必须由调用方实际提交。
- 旧23度预览保留，但不能完成新目标。
- 取消、跨会话或已完成任务不能被这个改口操作重开。

项目自动化测试合计 **178 项通过**。主应用网页与 Hermes 健康检查正常。

未覆盖：任意业务工具的自然语言改口解析、连续多次改口、语音识别期间的时序、真实车辆已执行动作的撤销、前台用户操作入口，以及方案二的并发子任务。当前结果是接入可行性和必要保护的验证，不是已上线的完整改口功能。

## 5. 对后续正式接入的建议

保持一个业务 task，增加明确的修改事件和有效目标版本；复用原生 steer，但同时完成：

1. 文字/S2S 的目标关联与歧义确认。
2. TaskManager 对已授权改口的继续监控。
3. 控制参数及完成回执的新旧版本检查。
4. 任务身份与当前目标分离，更新完成检测及过程展示。
5. 已完成任务收到修改时建立关联的新请求，而不是重写旧结果。

无需更换 Hermes，也无需实施方案二。是否正式接入当前页面，是本验证之后的独立改动。

## 6. 复现与隔离说明

```sh
uv run python scripts/probe_hermes_steer.py --repeats 2
uv run pytest tests/test_steer_probe.py -q
```

该脚本会使用真实模型额度，业务调用仍全部模拟。测试进程结束后关闭独立网关，记录保留在 `.runtime/steer-probe-*` 和 `test-results/`。未设置开机自启。

准备隔离环境时遇到 Hermes 依赖环境归属和 profile 自动发现限制；最终改用独立根目录，并只链接已有依赖环境。调试过程中创建的临时 profile 已通过 Hermes 自带删除流程清理，自动产生的 multiplex 配置已还原并核对。没有修改 Hermes 核心源码、主应用业务代码或默认模型凭据。
