# 工具发现：前置召回与按需搜索

状态：已实现并完成真实模型对照。后续已加入明确简单指令的精简候选策略及结论自动分类，见 [后续调整与实测](result-classification-design.md)。继续使用 Hermes；业务工具仍由 JSON 配置驱动。不是开启 Hermes 原生 Tool Search，也没有新增路由大模型。

## 两个时机

1. **第一次模型请求前**：明确控制请求使用原有元数据候选召回；同时带入关联的车况/车书定义与真实目录路径。控制候选最多 3 个，关联查询最多 4 个，整体上下文受 12000 字符预算限制。对原控制召回不能直接处理的查询、组合等请求，尝试全局词法召回，最多加载 4 个匹配定义；此类召回不会开启直接完成资格。
2. **执行中缺少能力时**：Hermes 可调用 `search_capabilities` 跨全目录搜索。匹配结果含完整 Schema 时直接 `call_tools`；预算不足时用 `describe_tools` 补取；未找到可靠候选时可改词或浏览目录。

工具定义可复用，不强制每轮重新查目录。相关查询定义只是可用能力，不是已取得的车况；明确的绝对设置不要求额外执行查询。复杂流程、失败诊断、追问、取消及最终结果校验继续由原机制处理。

## 检索算法与边界

`app/capability_search.py` 提供本地 BM25 检索，中文使用字符二元/三元片段，英文按单词切分。索引包括工具名称、别名、说明、示例、输入/输出 Schema 元数据与所在目录说明，名称和别名提高权重；屏蔽通用检索词，并设置匹配覆盖率下限。支持 `control / manual / status` 类型过滤。

这是词法检索，不是向量或完整语义理解。换说法、领域缩写或新概念仍可能漏召回，不能把零结果解释成“车辆不支持”。应通过配置别名、说明、示例改善覆盖，并保留补搜/浏览路径。排序分数不是正确率概率。

索引按不可变目录版本缓存，最多 8 份；检索只读取该任务固定版本中的启用工具。返回完整 Schema 时排除模拟实现与实际 profile 数据。检索本身不创建业务回执、改变车辆状态或报告控制成功。

## 通用 MCP 协议

六个入口：`search_capabilities`、`browse_capabilities`、`describe_tools`、`call_tools`、`request_user_input`、`finish_task`。完整定义见 `protocols/mcp-entrypoints.json`。

检索输入：当前任务及轮次、非空 `query`（最多 300 字符）、可选 `kind`、可选 `limit`（默认 4，最多 6）。输出含目录版本、匹配摘要、可用完整定义、真实目录路径、因预算未加载的定义标识、截断状态及本地耗时。整个响应最多约 12000 字符，匹配摘要和定义都计入预算。

第一轮候选中的控制候选标识与关联查询标识分开保存。关联查询不扩大“单项控制直接完成”的条件；查过数据、搜索过工具或发生错误后仍需按原流程提交结论。

## 可配置的关联关系

默认按目录路径去掉顶层领域后的部分关联，例如 `control/climate` 自动关联 `status/climate` 和 `manual/climate` 中启用的查询工具。

对于非同名类别，可以在现有目录 JSON 中添加可选 `related_query_paths`。例如在 `control.suspension.json` 中加入：

```json
"related_query_paths": [["status", "vehicle"]]
```

这只是配置示例，不是完整可导入的目录文件。该字段已加入目录与 bundle Schema，并验证目标必须是存在的车况或车书目录。完整 bundle 导入/导出会保留它；仅修改字段后重新加载即可生效，不需要把业务规则写进 system prompt。本次内置目录数据没有新增此字段，保持与基线相同的目录快照。

`CANDIDATE_RELATED_MAX_TOOLS` 默认 4，可调整关联查询上限。`CANDIDATE_PRELOAD_MAX_CHARS` 控制第一轮完整候选包预算。`discovery_mode=off` 关闭前置召回，但仍允许模型使用全局工具搜索；这可以模拟预加载未命中的路径。

## 页面与记录

“预加载候选工具”分别显示控制候选、查询候选与目录路径，明确提示尚未查询车况。“全局检索车辆能力”显示检索词、领域、匹配工具及完整参数是否提供。搜索调用写入 `catalog.searched` 和具体步骤计时，不冒充车辆查询。

## 实测结果

同一模型 `deepseek-v4.1-flash-1017`、同一目录快照和同一模拟配置，先跑修改前基线，再跑修改后版本。六条测试均校验通过。以下为后台任务耗时，不含 S2S：

| 指令 | 修改前 | 修改后 | 目录浏览/读取定义次数 |
| --- | ---: | ---: | ---: |
| 空调温度增加一度 | 35.19 秒 | 11.29 秒 | 6 → 0 |
| 主驾空调温度增加一度 | 37.58 秒 | 7.47 秒 | 6 → 0 |
| 全部分区空调设为 26 度 | 9.69 秒 | 2.58 秒 | 0 → 0 |
| 先查空调车书，再设为 23 度 | 20.24 秒 | 7.47 秒 | 7 → 0 |
| 未配备空气悬架，要求升高一档 | 14.50 秒 | 8.93 秒 | 7 → 0 |
| 空调温度增加一度，重复测试 | 24.10 秒 | 9.83 秒 | 3 → 0 |

绝对设定用例前后都是一次提供方请求，其耗时差异不能归因于搜索优化，体现了远端延迟波动。本次样本少、按版本顺序执行，不是随机交错的大规模统计测试。

相对温度用例仍出现过最终结论类型填写错误，导致额外修正；本次没有改变结论校验协议。因此没有声称它们都缩为两轮或三轮。提供方请求计数包含完成后可能启动又被取消的收尾请求，不能直接当成完整响应轮数。

另以关闭预加载的“查询当前空调温度”验证按需搜索：模型实际调用全局搜索，随后直接查询车况并提交结果，目录浏览/参数读取调用均为零，约 4.85 秒完成。该用例证明补搜入口实际可用，不是只测了第一轮预加载。

对照数据：`benchmarks/results/tool-discovery-comparison.json`。原始本机记录与截图位于被忽略的 `test-results/`。
